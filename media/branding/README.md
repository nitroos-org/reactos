# Nitro artwork

This folder holds the masters of the Nitro artwork and the scripts that turn them into the bitmaps and icons the
system builds. Only `wallpaper/Nitro.bmp` is built from here (see `CMakeLists.txt`); every other output replaces
a file elsewhere in the tree, in the format of the file it replaces.

## Concept (brand v7, "N + flame")

The mark is a dark navy squircle holding an N: two stems that run cyan to violet and a diagonal "flame" that runs
orange to yellow, with a narrow navy gap where the flame crosses the stems. The wordmark is "NitroOS" in Inter
Display SemiBold; the dot of the i is a small leaning bar in the flame orange. It replaces the v6 racing-stripe
mark (the layouts and file formats of every asset are unchanged; only the mark, the wordmark and the colours).

Geometry (512 grid, `tools/marks.py`): tile 16..496, superellipse exponent 6.5; N 246 x 268, stems 66, flame 80
wide horizontally (68 measured across the stroke, so it looks as heavy as the stems), gap 8. The small marks
(16, 20, 24, 32 px) are fitted to the pixel grid: whole-pixel stems, thicker strokes, flat colours (no gradient, no
banding in 4-bit and 8-bit icon frames), the flame's slope is exactly 1:2 so it steps evenly; 16 and 20 are
drawn without antialiasing on the N (five exact colours).

## Palette

`src/palette.css` is the one definition of the colours `render.py` uses; the SVG masters carry their own hex values.

| Name | Hex | Use |
|---|---|---|

| ink | `#0B0E1F` | tile bottom, darkest tone |
| harbor | `#2A2F66` | lighter navy: gradients, tile rim in the flat mark |
| sky | `#00C2FF` | cyan: the stems (bottom), accents on dark grounds |
| violet | `#7B5CFF` | the stems (top), glows |
| lamp | `#FF7A18` | flame orange, the i dot, banner line |
| glow | `#FFD23F` | flame yellow |
| mist | `#E4E8FF` | light tint |
| cloud | `#F4F5FB` | light background |
| slate | `#545A7A` | secondary text on light grounds |
| white | `#FFFFFF` | wordmark and text on dark grounds |

The boot screen has 16 colours (`BOOT` in `render.py`): 4 orange, 5 navy tile, 7 violet, 10 cyan, 11 yellow, 13
harbor (tile rim); the other indices stay neutral greys. The kept text bitmaps (copyright, shutdown, hibernate, bars)
used some of those indices as light-grey antialiasing levels; `boot_repalette` moves their pixels to the nearest
grey by brightness, so their text is unchanged. Index 15 stays white (the kernel fills the progress bar with it).

## Rebuilding

Run on a machine with `rsvg-convert`, Pillow, numpy and fontTools:

    python3 media/branding/tools/marks.py media/branding/src
    python3 media/branding/tools/wordmark.py media/branding/src
    python3 media/branding/tools/lockup.py media/branding/src
    python3 media/branding/tools/render.py . --sheet /some/dir
    python3 media/branding/tools/checkformats.py .

Resource files do not track the bitmaps they embed: after changing artwork, build from a fresh build directory or
delete the affected `.res` objects.

## The product name in the source

The rename is display only: version APIs, the registry ProductName, file, service and registry data names, paths
and URLs used by code keep their values. After merging new upstream code, list the display lines it added that
still spell the old name:

    python3 media/branding/rename-product.py --new-since <before-merge> <merge-commit>

Display strings that C/C++ can build from a macro use `BRAND_PRODUCT_NAME` / `BRAND_PRODUCT_NAME_W` (buildno.h,
from `NITRO_NAME` in `sdk/include/reactos/version.cmake`). Text that cannot (translated .rc tables, .inf/.ini/.mc,
setup language headers) spells "NitroOS" out; `rename-product.py` rewrites those when the name changes, and
`--new-since` lists lines main added that still say "ReactOS" or "Nitro" outside comments so they can be fixed by
hand (usually: replace with the macro, or with the literal name in a language table).

Build flags (golden/ISO): `-DBUILD_WOW64_ENABLED=ON -DSYSWOW64=ON` on amd64 Release (SYSWOW64=OFF hangs the
unattended install); i386 Debug `bootcdregtest` for the regtest ISO. `-DNITRO_VERSION=<release>` replaces the default
"dev <sha>" in the UI. The "dev <sha>" is read from the source tree's HEAD on every configure, and CMake is re-run
when HEAD moves (`.git/HEAD`, its ref and the HEAD reflog are CMake configure dependencies), so an incremental tree
shows the real head; `-DNITRO_SHA=<sha>` pins it.

.res gotcha: resource files do not track the bitmaps/icons they embed. After any artwork change, or when moving an
existing build tree to a commit that changed artwork, delete the affected `*.res` / `*.rc.obj` files (for
example `ntoskrnl/ntoskrnl.rc.res` for the boot logo) or build in a fresh directory; otherwise the old art stays in
the binary.
